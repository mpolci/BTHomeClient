# Design decisions

Record agreed decisions here. Proposed solutions and unanswered questions belong in the brief until resolved.

| ID | Date | Decision | Rationale / source |
| --- | --- | --- | --- |
| D1 | 2026-09-05 | Work on the current `ux` branch and track design in `docs/ux`. | Explicit product owner instruction. |
| D2 | 2026-09-05 | Historical data originates from sensor storage; do not build history from live reception. | Explicit product constraint; see R4 in the brief. |
| D3 | 2026-09-05 | The guest scenario uses the guest's own app installation and requires immediate live consultation without sensor registration. | Explicit product owner clarification; history and device interactions are not needed for guests. This does not imply a separate guest mode. |
| D4 | 2026-09-05 | History review should begin with a whole-period overview and support drilling into moments of interest. | Explicit product owner clarification; absences may last many months. Highlighting rules remain undecided. |
| D5 | 2026-09-05 | Show environmental and technical sensors together in the initial view. | The owner prefers all sensors together over the proposed separate technical group. |
| D6 | 2026-09-05 | Provide one command to download history from all compatible saved sensors. | Initial owner choice; superseded by D21, which uses opening history as the update trigger. |
| D7 | 2026-09-05 | Use broadcast sensor names to identify readings for guests. | The owner considers the broadcast name sufficient; sharing local metadata is not needed for this scenario. Firmware editability was not confirmed. |
| D8 | 2026-09-05 | Show registered sensors first and other detected sensors afterward, with clear visual differentiation. | Explicit owner preference to avoid confusing the two groups. This refines D5 without separating environmental and technical sensors. |
| D9 | 2026-09-05 | Use a vertical history overview with one compact chart per sensor for a shared measurement and period. Open a sensor in a single large detail chart with room for controls and comparison. | The owner explicitly accepted this direction after clarifying the smartphone layout. Fine interactions and visual styling remain to be evaluated. |
| D10 | 2026-09-05 | Replace fixed period selection as the primary history navigation with an immediate way to move through time. | The owner requested a slider or similarly direct mechanism. A draggable, resizable time window is being evaluated; its exact interaction is not yet approved. |
| D11 | 2026-09-05 | Keep the detail cursor fixed at the center, with sample date/time and recorded values always available. Pan data beneath it and zoom around the central time; allow endpoint samples to reach the center using empty space beyond the data. | The owner explicitly accepted this recommendation after finding tap positioning imprecise. This supersedes tap-to-position inspection in the wireframe. |
| D12 | 2026-09-05 | Show all available measured quantities directly in each live sensor entry. | Explicit owner choice after considering whether to emphasize one quantity and reduce the others. |
| D13 | 2026-09-05 | Registered sensors retain their latest available readings and remain listed. Use elapsed time since reception as the age indication. Remove unregistered sensors after five minutes without updates. | Explicit owner response to the stale-reading question. Persistence across restarts was subsequently confirmed in D27. |
| D14 | 2026-09-05 | Put the unregistered indicator beside the name and show a compact battery indicator only when reported by the sensor. | Explicit owner request to keep card heights consistent and include sensor battery information. |
| D15 | 2026-09-05 | Placement is an optional free-text description and does not group sensors into rooms. | Explicit owner choice during registration discovery. |
| D16 | 2026-09-05 | Retain the optional sensor image feature. | Explicit owner confirmation; an image is not required for registration. |
| D17 | 2026-09-05 | Prefill the registration name from the broadcast name and allow local editing. | Explicit owner confirmation; the edit does not change the name announced by the device. |
| D18 | 2026-09-05 | Show optional placement and image thumbnail in the live sensor card when present. | Explicit owner confirmation to aid sensor recognition. |
| D19 | 2026-09-05 | Place sensor status below the measurements, with reception age aligned left and the battery icon/percentage aligned right when reported. | Explicit owner approval after comparing alternative battery placements. Supersedes previous alignment experiments. |
| D20 | 2026-09-05 | Tapping a registered sensor prioritizes its history; sensor information remains secondary. | Explicit owner preference because sensor information is accessed infrequently. Behavior for sensors without history remains open. |
| D21 | 2026-09-05 | Automatically update individual history on opening it and all compatible saved sensors on opening the history overview. Keep existing data viewable and fall back to saved history when an update cannot complete; remove the separate download command. | Explicit owner confirmation of automatic bulk updating, extending the proposed per-sensor behavior. Supersedes D6. |
| D22 | 2026-09-05 | Show `History →` beside the name of registered sensors with history support and `Live only` in the same position for those without it. | Explicit owner approval after reviewing the visual trial; makes card behavior predictable. |

| D23 | 2026-09-05 | Revise one screen at a time: live cards open a sensor page, which holds management, registration, technical details, and history access. Show only a battery icon in live; put its exact percentage in the sensor page. Show reception age in live only for old readings. Remove card overflow menus and history capability labels. | Owner refinement and authorization of the revised sensor-page approach. Supersedes the affected presentation/navigation portions of D13, D19, D20, and D22. The staleness threshold was subsequently confirmed in D28; icon-level thresholds remain open. |
| D24 | 2026-09-07 | Approve the displayed sensor page with compact readings, immediately visible status and identification, and separate history and local-editing actions. Do not embed a history chart or start a history download merely on entering this page. | Explicit owner approval of the revised individual-screen wireframe. History updates remain tied to opening history. |
| D25 | 2026-09-07 | Edit local name and optional placement from fixed-position pencil buttons on the sensor page, each opening a text dialog with Cancel/Save. Select photos directly from the image area and support removal. Register an unregistered sensor with its broadcast name, then customize on the same page. | Explicit owner approval. Replaces the separate registration/editing form and the general local-editing action in D24; changes are saved individually. |
| D26 | 2026-09-07 | Place each editing pencil directly after its text, sized to match that text while retaining a larger touch target. | Explicit owner approval. Supersedes only the fixed-column placement in D25; does not change the fixed battery-icon position. |
| D27 | 2026-09-07 | Persist the latest available reading for registered sensors together with its original reception timestamp across app/process restarts. | Explicit owner confirmation. Restoring a reading does not make it fresh and does not create a live-derived historical series; R4 still applies. |
| D28 | 2026-09-07 | Treat readings as old at five minutes without an update. From that point show reception age on registered live cards; remove unregistered sensors at the same threshold. | Explicit owner confirmation. Registered sensors remain listed, and sensor-page reception age remains visible at all times. |
| D29 | 2026-09-07 | Removing a registration deletes the sensor's downloaded history from the app instead of retaining an archive. | The owner explicitly declined preserving downloaded history after removal. This does not authorize a reset of the physical sensor's memory. |
| D30 | 2026-09-07 | Approve the unregistered sensor page and same-page registration flow. Show identification, readings, reception age, reported battery level, and history capability before registration; reveal local editing after registration. | Explicit owner approval of the unregistered example and flow. |
| D31 | 2026-09-07 | Approve the registered live-only sensor page: show supported measurements and sensor information, explicitly indicate absent history support, and retain local editing/removal without a history-opening action. | Explicit owner approval of the live-only example. |
| D32 | 2026-09-07 | Approve the grouped connection/download, empty-history, unreachable-sensor, saved-data update, Bluetooth-disabled, and permission-unavailable states. Keep saved readings/history accessible and offer contextual retry or user-initiated prerequisite actions. | Explicit owner approval of the eight-state board. Chart exploration remains usable during updates and after update failures; exact platform wording and transfer recovery details remain open. |
| D33 | 2026-09-07 | Follow the latest native Android/Material visual direction as closely as practical, using platform-consistent components and theming. | Explicit owner style preference. Specific visual treatments remain subject to review; no Android dependency upgrade is implied by the style study. |
| D34 | 2026-09-07 | Prefer dark themes and reject the initial pale-blue palette. | Explicit owner feedback. Alternative palettes are under review; the Android/Material component direction remains unchanged. |
| D35 | 2026-09-07 | Use the dark Petrol palette as the selected visual direction. | Explicit owner choice after comparing Graphite, Petrol, and Amber. Material component structure and approved UX remain unchanged. |
| D36 | 2026-09-07 | Approve the full Material-style live screen with the dark Petrol palette and filled tonal sensor cards. | Explicit owner confirmation after reviewing the full screen. This establishes the visual reference for the remaining screens. |

| D37 | 2026-09-07 | Open History on the last seven days ending at the latest available recorded sample. Shorter archives fit their available coverage. Follow newly downloaded samples until the user chooses a time window; preserve an inherited overview window in detail and keep All history available. | Owner requested a one-week initial zoom and explicitly chose the latest recorded sample as the endpoint. Supersedes the native implementation's initial full-archive fit. |

The current live-screen and navigation revision is tracked in `live-v2.md`. Earlier decisions remain recorded with their superseding decisions above. History exploration, device controls, and other unresolved details continue in their respective documents.
